# 매일 할 일 — 이거 하나면 된다

> **바탕화면 「JGHBM 일일리포트」 더블클릭.** 끝.

매일 밤 21:00에 자동으로 돌아 리포트가 갱신된다. 사람이 실행할 것은 없다.
리포트를 열었을 때 **머리의 날짜 옆 배지**만 보면 된다:

| 배지 | 뜻 | 할 일 |
|---|---|---|
| `최신 (N일 전 종가)` | 정상 | 그날 숫자를 믿고 보면 된다 |
| `갱신이 하루 밀렸을 수 있다` | 주의 | 대개 공휴일. 하루 더 보고 계속 뜨면 아래 확인 |
| `자동 갱신이 멈췄을 가능성이 높다` | **문제** | 배너의 안내대로 `JVS_Daily` 실행 여부 확인 (0장) |

- **주말·공휴일에 금요일 데이터가 뜨는 것은 정상**이다. 장이 안 열렸으니
  새 데이터가 없다. 배지도 이를 감안해 영업일로 센다.
- 리포트가 어제 날짜 그대로여도 **배지가 `최신`이면 정상**이다.

## 언제 사람이 개입하나 — 세 가지뿐

| 상황 | 리포트에서 보이는 것 | 할 일 |
|---|---|---|
| **재무 경보** | `⛔ 경보 N건` + 종목 목록 | 3장. 대부분 즉시 조치 불필요 — 정기변경 때 검토 |
| **정기변경** | (6월·12월) | 2장의 보고 → 승인 → 반영 3단계 |
| **자동 갱신 멈춤** | 신선도 배지가 빨강 | 0장 로그 확인 |

그 외에는 **볼 것도 할 것도 없다.** 숫자가 매일 조금씩 움직이는 것은 시장이
움직여서다. 특히 CU·개인복제금액은 정수 주 격자라 가격이 조금만 변해도 답이
튄다 — 자릿수로만 읽으면 된다.

### ⚠ 왜 21:00인가 — `D:\data\_live` 접근 순서

이 레포는 `D:\data\_live`를 **읽기만** 한다. 그 파일을 **쓰는 것은
`JVS_Daily`(20:00)** 이고, `quant_lab\pit\build_live.py`를 체인으로 호출한다.
JVS 배치 파일이 "concurrent read/write를 피하려 별도 스케줄 대신 체인으로 묶었다"고
명시해 둔 이유다. 읽는 작업은 그 뒤에 서야 한다:

| 시각 | 작업 | `_live` |
|---|---|---|
| 20:00 | `JVS_Daily` | **WRITE** (build_live.py — 시작 후 1~1.5분 시점) |
| 20:30 | `delisting_radar_Daily` | read |
| **21:00** | **`JGHBM_daily`** | **read** |
| 21:30 | `ProjectQuant_Watchdog` | — |

> 처음 등록할 때 20:00으로 잡았다가 **JVS와 정면 충돌**하는 것을 발견해 옮겼다.
> 20:00에 두면 이 레포의 EOD 게이트가 시작 즉시 `_live`를 읽는데 JVS의 갱신은
> 1분 뒤라, **매일 갱신 전(전날) 데이터를 읽게 된다.** 리포트는 정상으로 보이지만
> 숫자가 하루씩 밀린다 — 조용해서 더 위험한 종류의 사고다.

`run_all.py`는 EOD 게이트를 내장해 장중에 돌면 스스로 멈춘다. 마감(15:30)만으로는
부족하고 `_live` 갱신까지 기다려야 한다(07-30 실측: 13:07 갱신분은 전날 종가까지만
담고 있었다).

### 등록에 쓴 명령 (재등록·다른 PC 이관용)

```powershell
$act = New-ScheduledTaskAction -Execute "cmd.exe" `
    -Argument '/c set "PYTHONUTF8=1" && "d:\dev\jeongga_hbm_etf\.venv\Scripts\python.exe" etf\run_all.py >> "d:\dev\jeongga_hbm_etf\etf\output\run_all.log" 2>&1' `
    -WorkingDirectory "d:\dev\jeongga_hbm_etf"
$trg = New-ScheduledTaskTrigger -Daily -At 21:00   # JVS_Daily(20:00) 뒤
$set = New-ScheduledTaskSettingsSet -StartWhenAvailable -DontStopOnIdleEnd `
    -ExecutionTimeLimit (New-TimeSpan -Minutes 30) -MultipleInstances IgnoreNew
Register-ScheduledTask -TaskName "JGHBM_daily" -Action $act -Trigger $trg -Settings $set
```

- **`set "PYTHONUTF8=1"` 의 따옴표가 중요하다.** `set PYTHONUTF8=1 &&` 로 쓰면
  `1` 뒤 공백까지 값에 들어가 `Fatal Python error: invalid PYTHONUTF8`로 죽는다
  (등록 첫 시도에서 실제로 겪음).
- `-StartWhenAvailable`: PC가 꺼져 있었으면 켜진 뒤 실행.
- `MultipleInstances IgnoreNew`: 앞 실행이 안 끝났으면 새로 띄우지 않는다.

## 2. 정기변경 (반기 1회 — 6월·12월)

리밸런싱은 **보고 → 승인 → 반영** 3단계다. 엔진이 정본을 직접 바꾸는 경로는 없다.

```powershell
# [사전] 판정 CSV 갱신 — 재실사·유동시총. 이게 리밸 심사의 입력이다.
#   data\processed\판정완료_20260725_실사확정.csv
#   data\processed\글로벌후보_실사_20260729.csv

# 1단계 [보고] — 정본 무접촉
.venv\Scripts\python.exe etf\run_rebalance_review.py
#   → etf\output\rebalance_proposal_<날짜>.csv (+ _diff.csv)
#   diff 표에서 볼 것: 신규/편출/군이동/비중Δ · ⚠버퍼유지 · 회전율 · 순도 변화

# 2단계 [승인] — 사람이 보고서를 읽고 판단

# 3단계 [반영]
.venv\Scripts\python.exe etf\run_rebalance_review.py --approve etf\output\rebalance_proposal_<날짜>.csv
#   → data\processed\구성표_확정_<날짜>.csv 승격 + 체크리스트 출력
```

승격 후 남은 절차(체크리스트가 화면에 다시 안내한다):

1. **두 상수를 모두** 새 구성표로 교체 — **코드 변경 = 의도 명시**라 일부러 수동이다.

   | 파일 | 상수 |
   |---|---|
   | `etf\run_tracking.py` | `CONSTITUENTS` |
   | `etf\hist_data.py` | `FINAL` |

   > 한쪽만 바꾸면 러너마다 다른 구성으로 산출된다(정본이 갈리는 사고).
   > `run_all.py`의 **[0a] 구성 진입점 게이트**가 이를 잡아 실행을 막으므로,
   > 게이트가 불일치를 알리면 나머지 한쪽을 마저 고치면 된다.

2. `etf\run_all.py` 로 산출물 전체 재실행 (같은 날 = 날짜 통일 원칙)
3. `make_pdf_etf.py` 재생성 후 커밋. 구 구성표는 역사 기록으로 보존한다.

버퍼 정책을 바꿔 보려면 `--buffer none|narrow|mid|wide` (기본 mid = 27%/67%).

## 6. 자주 겪는 상황

| 증상 | 원인 / 조치 |
|---|---|
| `[0a] 구성 진입점 불일치`로 중단 | 정기변경 반영 때 두 상수 중 한쪽만 바꾼 것. 메시지에 양쪽 파일명이 찍히니 나머지를 맞추면 된다(2장). |
| `run_all.py`가 "게이트가 막았습니다"로 중단 | parquet이 장중 스냅샷. **마감 후 `D:\data` 갱신을 기다린다.** |
| 게이트는 통과인데 "파이프라인이 N일 뒤처졌다" 경고 | 산출은 그 날짜 기준으로 일관되지만 최신은 아니다. 급하지 않으면 갱신 후 재실행. |
| 벤치마크만 실패 | KRX PDF 서비스 장애가 잦다. 러너가 직전 리포트를 보존하므로 방치해도 안전. 복구되면 `run_benchmark.py` 단독 실행. |
| CU·복제금액이 어제와 크게 다름 | **정수 주 격자는 톱니다.** 가격이 조금만 움직여도 답이 튄다. 그래서 두 지표 모두 "교란 전 시행 통과" 기준으로 고른다. 자릿수로 읽을 것. |
| 리포트 숫자가 이상함 | 머리글의 `구성:` 줄(`source_line`)과 `[출처]` 줄부터 확인. 어느 구성표·어느 데이터 소스를 썼는지 찍힌다. |
| `python run_all.py` → 파일 없음 | 스크립트는 `etf\` 안에 있다. `.venv\Scripts\python.exe etf\run_all.py` |
| 리포트 신선도 배지가 빨강 | `_live` 갱신이 멈춘 것. `Get-ScheduledTaskInfo -TaskName JVS_Daily`로 20:00 작업이 도는지 확인 → 안 돌면 그 레포 쪽 문제다. 이 레포는 읽기만 하므로 여기서 고칠 것은 없다. |
| 매일 같은 숫자만 나옴 | **스케줄 시각이 `_live` writer와 겹쳤을 때 생기는 증상**(0장 참조). `JGHBM_daily`가 21:00인지 확인 — 20:00이면 JVS 갱신 전에 읽어 매일 전날 데이터가 된다. |
| 한글이 `?????`로 깨짐 | `PYTHONUTF8=1` 누락. 스케줄러 액션은 `set "PYTHONUTF8=1"`처럼 **따옴표로 감싸야** 한다(0장). |
| PC를 껐다 켰더니 실행이 밀림 | `-StartWhenAvailable`이라 켜진 뒤 한 번 돈다. 정상이다. |

### 절대 하지 말 것

- **`D:\data`에 쓰지 않는다.** 이 레포는 읽기 전용 소비자다. 그 폴더는
  JVS/quant_lab이 소유하고 여러 프로젝트가 함께 읽는 공용 재료다.
- **`JGHBM_daily`를 20:00 이전으로 옮기지 않는다.** 0장의 접근 순서가 깨진다.
- **정기변경을 자동화하지 않는다.** 승인 게이트는 사람의 판단이 전제다.
